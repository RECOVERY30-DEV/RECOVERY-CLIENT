# Agent Harness

RECOVERY-CLIENT 하네스의 역할, 경계, 성장 기준을 설명합니다.

## 목적

- 에이전트가 작업 유형에 맞는 문서만 읽게 합니다.
- 사용자와 합의한 작업 방식을 세션마다 일관되게 적용합니다.
- 반복적인 누락과 위험한 명령을 체크리스트, 테스트, hook으로 줄입니다.
- 확인한 검증 결과와 남은 위험을 추적 가능하게 보고합니다.

## 계층별 책임

- `AGENTS.md`: 어디를 읽을지 알려주는 100줄 이하의 라우팅 허브
- `docs/`: 사람이 관리하는 규칙과 판단 근거의 source of truth
- `.agents/`: 문서 규칙을 적용하는 checklist, recipe, script
- `.codex/`: 세션 시작 context와 명령 실행 전 guardrail

같은 규칙을 여러 계층에 길게 복제하지 않습니다. 규칙이 바뀌면 `docs/`를 먼저 갱신하고 실행 자산을 맞춥니다.

## 기본 흐름

```text
User Request
-> AGENTS.md
-> working agreement와 핵심 rules
-> 작업별 docs와 pre-work checklist
-> 필요한 설계와 승인
-> 구현
-> 검증
-> final-report checklist
```

## 성장 기준

```text
지속적인 원칙이나 결정 -> docs
반복적으로 빠뜨리는 확인 -> checklist
일정한 순서의 반복 작업 -> recipe
조건 판단이 필요한 전문 작업 -> skill
결과가 결정적인 규칙 -> script, lint, test, hook
모든 PR에서 강제할 검증 -> CI
```

다음 신호가 보이면 에이전트가 자동화 후보를 먼저 제안합니다.

- 비슷한 작업 절차가 두 번 이상 반복됩니다.
- 같은 실수나 검증 누락이 반복됩니다.
- 사용자가 긴 절차를 다시 설명해야 합니다.
- 입력과 출력 형식이 안정적입니다.
- 여러 파일이나 도구를 일정한 순서로 다뤄야 합니다.

후보를 제안할 때는 이름, 반복 근거, 추천 형태, trigger, 입력과 결과, 검증 방법을 설명합니다. 승인을 받기 전에는 관련 파일을 만들지 않습니다.

## 현재 범위

- 라우팅 문서와 핵심 프로젝트 규칙
- 작업 전, 검증, 최종 보고 체크리스트
- 독립적인 회의적 PR 리뷰 recipe
- 하네스 구조 검사와 단위 테스트
- SessionStart primer와 shell guard 및 단위 테스트

## Codex hook 활성화

- 프로젝트 로컬 hook은 저장소가 신뢰된 상태에서만 로드됩니다.
- 처음 받았거나 `.codex/hooks.json`이 변경된 뒤에는 Codex에서 hook 정의를 검토하고 신뢰해야 합니다. CLI에서는 `/hooks`로 상태를 확인합니다.
- 신뢰하기 전에는 hook이 건너뛰어질 수 있으므로, hook만을 유일한 보안 경계로 간주하지 않습니다.

## 이후 추가 시점

- CSS와 품질 도구 도입 시 lint, format, test 규칙과 검증을 추가합니다.
- 실제 페이지 패턴이 반복되면 page recipe, spec, skill을 검토합니다.
- API 문서와 데이터 계층이 정해지면 API intake, integration, verification skill을 검토합니다.
- 검증 skill이 둘 이상 생기면 통합 verifier를 검토합니다.
- CI는 별도 작업에서 하네스와 애플리케이션 검증 명령을 실행하도록 연결합니다.

## 유지보수

- 모델이나 주요 도구가 바뀌면 대표 작업으로 하네스를 재검증합니다.
- 오래된 경로, 명령, 라이브러리 이름을 정기적으로 제거합니다.
- 사용하지 않거나 책임이 겹치는 recipe와 skill은 합치거나 삭제합니다.
- 하네스는 원본 프롬프트, 비밀정보, 세션 로그를 저장하지 않습니다.
