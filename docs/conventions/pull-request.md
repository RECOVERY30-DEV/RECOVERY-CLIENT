# Pull Request Convention

PR의 목적, 판단 근거, 검증 결과를 한 번에 이해할 수 있게 하는 기준입니다.

## 대상 브랜치

- 기능, 수정, 초기 설정 PR은 `develop`을 대상으로 합니다.
- `main` 대상 PR은 검증된 `develop`을 배포 가능한 상태로 승격할 때만 사용합니다.
- base와 head가 의도한 브랜치인지 생성 전후에 확인합니다.

## 제목

commit과 같은 형식을 사용합니다.

```text
type: 한글 작업 내용
```

- PR 전체 결과를 대표하는 type 하나를 선택합니다.
- 구현 세부보다 사용자가 리뷰할 변경 목적을 표현합니다.
- Jira나 issue가 있으면 본문에 연결하고 제목에는 반복하지 않습니다.

## 상태

- 작업 또는 논의가 남아 있으면 Draft로 생성합니다.
- 필요한 구현과 검증이 끝나고 리뷰 가능한 상태일 때 Ready로 전환합니다.
- 에이전트는 명시적인 요청 없이 PR 상태를 변경하거나 merge하지 않습니다.

## 본문 구조

변경 규모에 맞게 아래 순서를 사용하고, 해당 내용이 없으면 억지로 길게 작성하지 않습니다.

```markdown
## 📌 요약

## 📚 작업 내용

## 🔎 상세 설명

## 💭 고민한 부분

## 🧪 검증
```

- 요약: PR이 해결하는 문제와 최종 결과
- 작업 내용: 리뷰 순서에 맞춘 주요 변경
- 상세 설명: 기존 문제, 책임 경계, 중요한 동작
- 고민한 부분: 고려한 선택지, 최종 선택 이유, 남은 위험
- 검증: 실제 실행한 명령과 결과, 실행하지 못한 항목과 이유
- Jira 또는 issue: 실제 연결 항목이 있을 때만 작성

## 변경 범위

- 하나의 목적을 가진 review 가능한 크기로 유지합니다.
- 관련 없는 refactor, dependency, formatting 변경을 섞지 않습니다.
- 큰 작업은 기준 문서, 기반 설정, 기능 구현처럼 독립적으로 검증 가능한 PR로 나눕니다.
- PR 본문과 실제 diff가 다르면 merge 전에 본문을 갱신합니다.

## Stacked PR

선행 PR에 의존하는 작업은 Stacked PR로 구성할 수 있습니다.

- 본문에 선행 PR과 의존 이유를 명시합니다.
- base branch와 최종 merge 순서를 적습니다.
- 간단한 branch tree로 관계를 보여줍니다.
- 선행 PR이 변경되면 후속 PR의 diff와 검증을 다시 확인합니다.

## 리뷰와 Merge

- 작성자의 완료 설명보다 diff와 검증 결과를 근거로 판단합니다.
- 혼자 작업하더라도 `.agents/recipes/skeptical-pr-review.md` 기준으로 문제와 누락을 점검합니다.
- unresolved review comment와 실패한 검증이 있으면 Ready 또는 merge 상태로 보지 않습니다.
- commit, push, PR 생성·수정, Ready 전환, merge는 각각 명시적으로 요청받았을 때만 수행합니다.
