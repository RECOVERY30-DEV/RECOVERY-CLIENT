# Skeptical PR Review Recipe

구현과 평가의 컨텍스트를 분리해 PR의 문제점과 누락을 찾을 때 사용합니다.

## 원칙

- 가능하면 구현을 수행한 작업과 분리된 새 작업이나 독립된 reviewer가 검토합니다.
- 좋은 점을 나열하기보다 결함, 회귀, 누락된 검증, 불명확한 가정을 우선 찾습니다.
- 작성자의 완료 보고를 근거로 삼지 않고 요구사항, diff, 코드, 실행 결과를 직접 확인합니다.
- formatter나 CI가 판별할 수 있는 사소한 스타일보다 동작과 위험을 우선합니다.

## Workflow

1. PR 목표와 명시된 비목표를 확인합니다.
2. base와 head, 전체 diff, 변경 파일을 확인합니다.
3. 사용자 흐름, 에러 처리, 경계 조건, 보안, 접근성, 성능 회귀를 점검합니다.
4. 테스트가 실제 변경 동작을 검증하는지 확인합니다.
5. 실행된 검증과 실행되지 않은 검증을 구분합니다.
6. 문제를 심각도, 파일 위치, 원인, 수정 방향과 함께 보고합니다.

## Output

```markdown
## Findings

- [Severity] `path:line` 문제와 영향
  - 원인:
  - 권장 수정:

## Verification Gaps

- 실행되지 않았거나 충분하지 않은 검증

## Residual Risks

- 자동 검증으로 확정할 수 없는 항목
```

리뷰 요청만 받은 경우에는 사용자 승인 없이 수정, commit, push, merge를 수행하지 않습니다.
